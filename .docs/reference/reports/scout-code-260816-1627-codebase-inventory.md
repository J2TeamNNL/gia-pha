## 3. Database layer (`src/db/`)

### Schema & migrations — `src/db/schema.ts`
- `LATEST_SCHEMA_VERSION = 3` (`schema.ts:1`).
- Three migrations in `SCHEMA_MIGRATIONS` (`schema.ts:197-201`):
  1. v1 `INITIAL_SCHEMA_SQL` (`schema.ts:16-54`): `persons` (flat fields: name parts, gender, is_living, birth/death y-m-d, death_lunar, burial_location, contact fields, avatar/bio/notes, `is_anchor`) and `relationships` (`person_id`, `related_to_id`, `rel_type`, `is_primary`, FKs `ON DELETE CASCADE`).
  2. v2 `DOMAIN_SCHEMA_SQL` (`schema.ts:56-190`): richer genealogy domain tables not yet wired to any TS repository code — `tree_metadata` (singleton, schema_version, reference_person_id), `partial_dates` (calendar/precision-aware dates incl. lunar, ranges, approximate, text-only), `places` (hierarchical via `parent_place_id`), `family_unions` (status enum), `family_partners` (role, position, unique per union+person and per union+position), `family_children` (parentage_type, birth_order), `events` (person- or union-linked, privacy_level), `import_batches`, `external_references`, `extension_payloads` (GEDCOM-style import/extension scaffolding). Indexes on `family_partners.person_id`, `family_children.child_person_id`, `events.person_id`/`family_union_id`. Trigger `family_children_no_partner_self_link` blocks a person being both partner and child of the same union.
  3. v3 `RELATIONSHIP_INDEXES_SQL` (`schema.ts:192-195`): indexes `relationships(person_id)` and `relationships(related_to_id)`.
- `applyMigrations(executor: MigrationExecutor)` (`schema.ts:221-248`): runs each pending migration in its own `BEGIN IMMEDIATE`/`COMMIT`, rolls back on failure and rethrows; always sets `PRAGMA foreign_keys = ON` first; keeps `tree_metadata.schema_version` in sync for migrations ≥ v2.
- `migrationsAfter(version)` (`schema.ts:203-208`), `isSchemaValid(db)` (`schema.ts:256-266`), `initDatabaseSchema` (`schema.ts:251-254`, back-compat entrypoint applying v1+v2 SQL directly).

### Connection / persistence — `src/db/client.ts` + `src/db/sqlite.worker.ts`
- All SQL runs inside a dedicated Web Worker (`sqlite.worker.ts`) using `@sqlite.org/sqlite-wasm`'s `oo1.OpfsDb` — persistence is OPFS-backed, synchronous within the worker, no explicit flush needed (comment at `persons.ts:1-6`).
- `client.ts:173-201` `getDb()`: lazily spawns `src/db/sqlite.worker.ts` as a module worker, caches the client promise, tears down and allows respawn on fatal worker error.
- `getDatabaseRuntimeError(environment)` (`client.ts:43-67`): checks `Worker` support, `isSecureContext`, `crossOriginIsolated` + `SharedArrayBuffer`, and OPFS (`navigator.storage.getDirectory`) — returns a `DatabaseRuntimeError` describing the first missing requirement, or `null`.
- `SqliteWorkerClient` class (`client.ts:69-169`) implements request/response correlation over `postMessage` by incrementing id; exposes `exec`, `run`, `close`, plus catalog ops.
- Multi-tree "catalog" concept lives in the worker: `sqlite.worker.ts` maintains a **catalog DB** (`/gia-pha.catalog.sqlite3`, table `trees` + `catalog_metadata`) separate from each **tree DB** (`/trees/<uuid>.sqlite3`). Only one tree DB is open at a time (`treeDatabase`, `activeTreeId` module state, `sqlite.worker.ts:41-42`).
  - `initialize()` (`sqlite.worker.ts:158-170`): opens catalog, runs `migrateLegacyTreeIfNeeded()` (imports a pre-multi-tree `/gia-pha.sqlite3` file as `LEGACY_TREE_ID` if the catalog is empty and that legacy file exists — `sqlite.worker.ts:145-156`), reopens the previously-active tree if one is stored.
  - `createTree`, `renameTree`, `openTreeDatabase`, `deleteTreePersisted` (`sqlite.worker.ts:211-266`) manage catalog rows + OPFS files; delete requires `confirmed=true` (enforced by `requireDeleteConfirmation` in `catalog.ts:21-25`) and restores the connection if the OPFS file delete fails.
  - `handle(request)` (`sqlite.worker.ts:268-299`) is the single dispatch point for all `WorkerCommand` types; requests are serialized through `workQueue` (`sqlite.worker.ts:305-311`) so no two run concurrently.
- `src/db/catalog.ts`: `TreeMetadata`, `ActiveTreeMetadata` types; pure helpers `normalizeTreeName` (trim/collapse whitespace, ≤120 chars), `requireDeleteConfirmation`, `selectNextActiveTree` (picks another tree after the active one is deleted).
- `src/db/protocol.ts`: shared `WorkerCommand`/`WorkerRequest`/`WorkerResponse`/`QueryResult`/`SqlValue` types — the postMessage contract both sides import from, per file-top comment (`protocol.ts:1-5`).

## 6. Graph traversal code (most important section)

Two independent traversal implementations exist, at different layers, for different purposes — **neither exposes an ego→target path/kinship primitive today**:

1. **`src/db/validation.ts:38-61`** — `hasDirectedPath(relationships, fromId, toId): boolean`
   - DFS (explicit stack, `visited` set) strictly over parent→child edges (`PARENT_OF`/`ADOPTED_PARENT_OF`), direction `person_id → related_to_id`.
   - Answers only "is `toId` a descendant of `fromId`" (boolean reachability), used exclusively to block cycle-creating relationship inserts (`validation.ts:93-96`). Does not return the path, does not consider spouse edges, does not compute generational distance.

2. **`src/graph/layout.ts`** — `computeLayout(input: LayoutInput): LayoutResult` (`layout.ts:111-242`), the only code that walks the whole graph for rendering:
   - `buildAdjacency(relationships)` (`layout.ts:68-87`) builds three adjacency maps from the flat relationship list: `parentsOf`, `childrenOf` (both from `PARENT_TYPES = {PARENT_OF, ADOPTED_PARENT_OF}`), `partnersOf` (from `COUPLE_TYPES = {SPOUSE, EX_SPOUSE}`).
   - `assignGenerations(focusId, adjacency): Map<personId, generation>` (`layout.ts:90-109`) — **BFS from a single focus/ego person**, generation `-1` per parent hop, `+1` per child hop, `0` for partners (same row). This is the closest thing to an ego-centric traversal in the codebase, but it:
     - is undirected/unweighted BFS assigning a signed integer "generation," not a labelled kinship path;
     - does not record *how* a person was reached (no parent-pointer/path reconstruction — only final generation number is kept);
     - stops at first-discovered generation per node (a node's generation is fixed by whichever BFS frontier reaches it first; no shortest-path-if-multiple-paths handling beyond BFS order);
     - mixes ego-to-target traversal with **rendering/layout** concerns (depth filtering, `MAX_VISIBLE_NODES = 500` cap, row ordering, x/y coordinate assignment) in the same function — there is no standalone "get all ancestors/descendants of X" or "shortest relationship path between A and B" function.
   - `computeLayout` runs in a Web Worker (`src/graph/layout.worker.ts:15-27`) via `useGraphLayout(input)` hook (`src/graph/useGraphLayout.ts:13-56`), which falls back to synchronous `computeLayout` when `Worker` is undefined (unit tests).
   - Orphan handling: persons not reached by BFS from focus get placed at `orphanGeneration = max(known) + 1` (`layout.ts:126-132`) so they don't vanish — relevant if a "xưng hô" feature must handle disconnected persons gracefully.

**For a new ego→target kinship-term feature**, there is no existing "walk from person A to person B and describe the relationship path" function anywhere in the codebase. The nearest reusable primitives are `buildAdjacency` (adjacency-map construction, `layout.ts:68-87`) and the generation-BFS pattern in `assignGenerations` (`layout.ts:90-109`), both currently private to `layout.ts` (not exported for reuse) except via the exported `computeLayout` entrypoint. `hasDirectedPath` in `validation.ts` is parent-edge-only reachability and is the only other traversal function in the repo.
